# Stage 5 — калибровка requests/limits

## Как мерили

- Один под, автоскейлеров нет (VPA в режиме `Off` только собирает рекомендации).
- Реальная тестовая картинка: `sample.png` (709×682, плотный английский текст),
  OCR занимает **~2.8 с** при одиночном запросе.
- k6 (`load/calibrate.js`) даёт постоянное число параллельных запросов (closed loop,
  без think time), по 60 с на ступень: 1, 2, 4, 8, 12, 16.
- CPU/RAM пода — из Prometheus (`container_cpu_usage_seconds_total`,
  `container_memory_working_set_bytes`), p95/ошибки — из k6.
- k6 и Prometheus работают на том же узле, что и приложение: часть CPU они забирают
  себе. Это систематическая погрешность стенда (оговорено в выводах).

### Что это значит

- Пропускная способность **упирается в ~0.37 RPS** и дальше не растёт.
- Латентность растёт почти линейно с числом одновременных запросов:
  очередь копится, а CPU уже занят на ~1.8 из 2 ядер.
- При 16 VU часть запросов не успевает за 60-секундный таймаут k6 → 12.5% ошибок.
- Точка насыщения — **1–2 одновременных запроса**. «Умеренной нагрузки», при которой
  под бы использовал, скажем, 30% CPU, на этом узле просто нет: один OCR-запрос
  уже занимает ядро.
- Причина не только в 2 vCPU: `pool.default.max=2` в приложении разрешает 2 процесса
  tesseract на под, но оба процесса делят те же 2 ядра.

## Рекомендация VPA (режим Off, после калибровки)

```
lowerBound: cpu 250m, memory 256Mi
target:     cpu 920m, memory 256Mi
upperBound: cpu 1,    memory 2Gi   (упёрлось в maxAllowed)
```

VPA тоже говорит: по CPU поду нужно ~0.9–1 ядро, по памяти — 256Mi.

> Позже, чтобы 2 пода VPA-сценария помещались на узел, `maxAllowed.cpu` был
> снижен до `500m`. Поэтому в финальных прогонах C/E target CPU = **500m**
> (искусственный потолок), а не 920m. Память не менялась: target 256Mi.

## Принятые значения (записаны в `k8s/base/deployment.yaml`)

| Параметр | Значение | Почему |
|---|---|---|
| `requests.cpu` | **400m** | компромисс: позволяет поставить 3 пода на узел (3×400m + 780m системных/мониторинга = 1980m ≤ 2000m) |
| `requests.memory` | **256Mi** | совпадает с target VPA; реальный пик ~145Mi |
| `limits.memory` | **384Mi** | ~2.6× пика, запас на вариативность изображений |
| `limits.cpu` | не задан | чтобы не добавлять throttling |
| реплики A | **3** | столько же, сколько максимум у HPA — честный baseline |
| `maxReplicas` B/D | **3** | больше не помещается на узел |
| пик нагрузки k6 | **10 VU** | создаёт очередь и загрузку CPU, но без массовых 60-секундных таймаутов |

### Важная оговорка

400m CPU — **не «правильный» request с точки зрения потребления**. Измерения
показывают ~1.8 ядра на под при насыщении; VPA рекомендует ~920m. Если поставить
920m, на узле поместится только один под (920m + 780m системных > 2000m), и HPA
физически не сможет масштабироваться. Поэтому 400m выбран осознанно, чтобы
*вообще иметь возможность* наблюдать HPA/VPA на одном узле. Это ограничение
стенда, а не рекомендация для продакшена.

Следствие: при нагрузке HPA будет видеть утилизацию `~1800m / 400m = 450%` и
всегда захочет `maxReplicas`. Это ожидаемо и будет видно на графиках. Реальный
выигрыш дало бы не число подов, а более крупный узел (4+ vCPU) или несколько узлов.
