## 3. Что известно про приложение (из исходников, а не по догадкам)

`src/providers/http/index.ts` и `src/argv/yargs.ts`:

| Параметр | Значение |
|---|---|
| Порт | `8884` (env `PORT` или `--http.listen.port`) |
| OCR-эндпоинт | `POST /tesseract` |
| Формат тела | `multipart/form-data` |
| Поле файла | `file` (`http.input.fileField`) |
| Поле опций | `options` — **строка с JSON**, не JSON-часть (`http.input.optionsField`) |
| Health | `GET /.well-known/health/{ready,live,healthy}` |
| Статус | `GET /status` |
| Web UI | `GET /` |
| Ответ успеха | `200 {"data": {..., "stdout": "<распознанный текст>", "stderr": "..."}}` |
| Ошибка валидации | `400`, ошибка обработки — `500`, тело `{"error": ..., "reason": ...}` |

Опции (`options`): `languages` (массив строк, например `["eng"]`), `dpi` (int > 0),
`pageSegmentationMethod` (0–13), `ocrEngineMode` (0–3), `tessDataDir`, `userPatternsFile`,
`userWordsFile`, `configParams` (dict string→string).

**Важная деталь для нагрузки:** `pool.default.max = 2` — внутри одного пода tesseract
запускает максимум 2 процесса OCR, остальные запросы **встают в очередь**.
Это ограничивает пропускную способность пода и напрямую влияет на калибровку (Stage 5)
и на число VU в k6.

Пример запроса:

```bash
curl -sS -X POST http://127.0.0.1:8884/tesseract \
  -F 'file=@sample.png' \
  -F 'options={"languages":["eng"],"pageSegmentationMethod":3}'
```

## 4. Термины простыми словами

- **Node (узел)** — виртуальная машина (EC2), на которой работает Kubernetes. У неё есть
  CPU и RAM, которые делятся между подами.
- **Pod** — самый маленький запускаемый объект: один или несколько контейнеров с общими
  сетью и хранилищем. Это «экземпляр» приложения.
- **Deployment** — менеджер подов: следит, чтобы было запущено нужное число одинаковых подов,
  пересоздаёт упавшие, умеет обновлять образ. Сам поды не «держит» руками — этим занимается он.
- **Service** — стабильная точка входа (имя + виртуальный IP), которая балансирует трафик
  между подами, подходящими под `selector`. Поды меняются, а адрес Service — нет.
- **requests** — сколько CPU/RAM под **гарантированно резервирует** на узле. Планировщик
  ищет узел, где есть столько свободного места. HPA считает утилизацию CPU **от requests**,
  поэтому неверные requests ломают автоскейлинг.
- **limits** — верхняя граница. Превышение лимита **памяти** → процесс убивают (`OOMKilled`,
  рестарт). Превышение лимита **CPU** → процесс не убивают, а «притормаживают»
  (`throttling`), из-за чего растёт латентность.
- **allocatable** — CPU/RAM узла, реально доступные подам: `capacity` минус резерв
  системы и kubelet. Именно от allocatable считается, сколько подов поместится:
  `floor(allocatable_cpu / cpu_request)`.
