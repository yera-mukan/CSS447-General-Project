# Stage 8 — расчёт стоимости (`scripts/cost.py`)

## Формулы и что они значат

Обозначения: `T` — длительность прогона в часах, `P` — цена узла (`$0.10175/ч`
для `m7i-flex.large`), `NODE_VCPU=2`, `NODE_RAM=8 GiB`.

```
node_cost       = P * T
cpu_share(t)    = Σ cpu_requests(t) / NODE_VCPU
mem_share(t)    = Σ mem_requests(t) / NODE_RAM
alloc_share(t)  = max(cpu_share(t), mem_share(t))
allocated_cost  = P * ∫ alloc_share(t) dt
idle_cost       = node_cost - allocated_cost
cost_per_1k     = allocated_cost / (успешные_запросы / 1000)
efficiency      = ∫ реальное_использование dt / ∫ requests dt
```

- `node_cost` — **реальный счёт AWS** за узел за время прогона. Он не зависит
  от числа подов: инстанс уже запущен и оплачивается целиком.
- `cpu_share` / `mem_share` — какую долю узла мы **зарезервировали** (requests),
  а не сколько реально использовали.
- `alloc_share = max(...)` — «доминирующий ресурс». Если CPU зарезервирован
  на 80%, а память на 10%, под всё равно ограничен CPU; складывать доли с
  произвольными весами было бы менее честно.
- `allocated_cost` отвечает на вопрос: **сколько стоили бы зарезервированные
  ресурсы, если бы размер узла следовал за подами**. Это модельная величина,
  а не строка в счёте AWS.
- `idle_cost` — оплачено, но не зарезервировано нашими подами (системные поды,
  мониторинг, запас).
- `cost_per_1k` — сколько модельных денег уходит на 1000 успешных OCR-запросов.
- `efficiency` — во сколько раз реальное потребление CPU (или RAM) меньше
  requests. Значение 1.04 в прогонах означает, что CPU использовался даже
  чуть больше requests (мы специально занизили request ради 3 реплик).

Интеграл считается методом трапеций по range-запросам Prometheus с шагом 15 с.
Пропущенные точки считаются нулём.

## Почему реальный счёт AWS не меняется от числа реплик

HPA/VPA меняют только поды внутри уже оплаченного EC2. Пока узел один,
`node_cost` постоянен. `allocated_cost` — это мысленный эксперимент:
«если бы под каждый набор requests выделялся узел подходящего размера».
Именно поэтому в таблице сравнения смотрим и `node_cost` (факт), и
`allocated_cost`/`cost_per_1k` (эффективность использования железа).

Если бы был Cluster Autoscaler/Karpenter, при нехватке места добавлялись бы
новые EC2, и уже `node_cost` реагировал бы на нагрузку. На одном узле
`maxReplicas` упирается в allocatable, а счёт — нет.

## Что ещё в реальном счёте AWS (не в модели)

- EBS-том 30 GiB (gp3) — примерно $2.4/мес;
- публичный IPv4 — около $3.65/мес;
- исходящий трафик (egress) — в лаборатории минимален;
- снимки EBS, если включены.

## Sanity check

`node_cost` за 10 минут при $0.10175/ч ≈ **$0.0170**. Это же значение даёт
`$0.10175 * 730 ≈ $74.3/мес` при непрерывной работе. AWS Cost Explorer по тегу
инстанса должен сойтись с точностью до округления, но его данные приходят
с задержкой (несколько часов).

## Запуск

```bash
python3 scripts/cost.py \
  --start 2026-11-19T17:11:06Z --end 2026-11-19T17:21:07Z \
  --prom-url http://127.0.0.1:19090 \
  --k6 results/B-hpa-50-1/k6.json \
  --price 0.10175 --vcpu 2 --ram-gib 8 \
  --out results/B-hpa-50-1/cost.md
```

`run-scenario.sh` вызывает это автоматически и кладёт результат в
`results/<scenario>-<rep>/cost.md`, а JSON-версию — в `cost.json`.
